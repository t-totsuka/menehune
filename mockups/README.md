# UI モックアップ集

暦・天文と投稿の画面を、ワイヤーフレームとハイフィデリティの 2 段階でレビューするためのモックアップ集です。
モック本体は HTML・CSS・classic script だけでできており、サーバの起動やビルドは不要です。外部ネットワークにも接続しません。
表示しているサンプル値（暦・天文・天気・投稿など）はすべて架空で、正確さは検証していません。

## 開き方

1. エクスプローラーなどで `mockups/index.html` をブラウザ（Chrome、Edge、Firefox の最新版）で直接開きます（`file://` で開く）。
2. 一覧ページから、画面ごと・段階ごとのモックを開きます。各画面には一覧へ戻る導線があります。
3. 幅の比較は `viewer.html?screen={画面ID}` で、375px と 1440px を並べて確認できます。

その他のページ：

| ページ | 内容 |
|--------|------|
| `components.html` | 部品ギャラリー（mk-* 部品を状態ごとに一覧表示） |
| `tokens.html` | デザイントークンの見本 |
| `glossary.html` | 日英用語集と日付時刻の書式 |
| `a11y.html` | アクセシビリティの方針（代替テキスト、フォーカス、色以外の区別） |

一覧（`index.html`）、幅プレビュー（`viewer.html`）と上の 4 ページをカタログページと呼びます。各カタログページの先頭には共通のナビゲーションがあり、ほかのカタログページへ移動できます。

### カタログページの規約

- **文言は日本語の固定**：カタログページはレビュー用のページで、製品の UI ではありません。文言はページに日本語で直接書き、`data-i18n` のキーは付けません。辞書（`assets/i18n/messages.*.js`）は読むだけにして、カタログページのために編集しません。
- **共通のナビゲーション**：`<body>` の先頭（`<main>` の前）に、`<nav class="mk-catalog-nav" aria-label="カタログ">` と、6 ページへのリンクの一覧を置きます。並びは、一覧、幅プレビュー、部品ギャラリー、トークン、用語集、アクセシビリティです。そのページ自身へのリンクに `aria-current="page"` を付けます。見た目は `review.css` にあり、レビュー用ツールバーと同じく、テーマと段階によらないグレーの表示です。
- **スタイルの置き場所**：共通の見た目（ナビゲーション）だけを `review.css` に置きます。ページ固有のスタイルは、そのページの `<head>` の `<style>` に書き、共通の CSS ファイルには足しません。製品の部品や見た目を見せる箇所では、製品のトークンを使います。
- **読み込むファイル**：画面と同じ CSS と JS を同じ順に読み込みます（`theme-boot.js` は `<head>`、ほかは `<body>` の末尾）。そのため、レビュー用ツールバー、テーマ、段階、辞書の読み取り、mk-* 部品をどのカタログページでも使えます。ページ固有の処理は、それらの後にインラインのスクリプトで書きます。
- **編集の範囲**：カタログページを作り込むときは、そのページのファイルだけを編集します。

## URL パラメータ

画面の表示状態は URL パラメータで切り替えます。画面下部のレビュー用ツールバーからも切り替えられます。

| パラメータ | 値 | 既定値 | 保存 |
|------------|----|--------|------|
| `stage` | `wireframe`、`hifi` | `hifi` | する |
| `lang` | `ja`、`en` | `ja` | する |
| `theme` | `system`、`light`、`dark` | `system` | する |
| `auth` | `guest`、`member`、`admin` | `guest` | しない |
| `scenario` | `default`、`empty`、`fetch-error`、`validation-error`、`private-blocked`、`hidden-own`、`hidden-other`、`deleted-comment`、`no-location`、`weather-failed`、`provisional-holiday` | `default` | しない |

- 優先順位は、URL パラメータ、保存値（`localStorage`。使えない環境では保存しません）、既定値の順です。
- `auth` と `scenario` は画面ごとに許可する値が決まっています（`data/screens.js`）。許可されていない値は既定値になり、ツールバーに警告が出ます。
- 例：`screens/post-detail.html?stage=wireframe&lang=en&theme=dark&auth=member&scenario=hidden-own`

## レビューの進め方

1. **ワイヤーフレーム**：`stage=wireframe` で、配置・情報の構成・画面遷移をレビューします。色はグレーのみで、装飾は表示しません。
2. 指摘を反映し、`data/screens.js` の各画面の `review.wireframe.status` を `draft` → `in-review` → `changes-requested` / `approved` と更新します。
3. **ハイフィデリティ**：全画面のワイヤーフレームが `approved` になってから着手します。ワイヤーフレームが未承認の画面をハイフィ段階で開くと、「未確定」のバナーが出ます。
4. ハイフィのレビューで配置の変更が必要になった場合は、ワイヤーフレームの状態を `in-review` に戻します。マークアップは 1 つなので、変更は両方の段階に反映されます。

### ワイヤーフレームのレビューで確認してほしい論点

実装中に判断を保留した点です。レビューで結論を出し、`data/screens.js` のレビュー状態に記録してください。

- **星図**：日本語表示では、ラベルの置き場所が足りず、オリオン座・ペルセウス座・アンドロメダ座の名前を省いています（代替テキストには残ります）。また、日時と地点の入力欄はモックで、値を変えても星図は描き直しません（画面に注記があります）。
- **トップ**（2026-11-19 の指摘をタスク 8.1 で反映、再レビュー待ち）：
  - 天文現象の絞り込みは、閉じたアコーディオン（「期間と種類で絞り込む」）にしました。
  - 960px 以上で 1:3 の 2 列にしています（狭い側は 15rem より細くしないので、960px 付近では 1:3 より投稿の側が少し狭くなります）。2 列にする幅は 960px でよいか、1280px からにするか。
  - 狭い幅では 1 列で、未ログインの案内、今日の暦、投稿、天文現象の順にしています。投稿を主な内容とするため、天文現象より先に置きました。この順は読み上げとキーボードの移動の順と同じで、PC 幅では左の列（案内・今日の暦）、右の列（投稿）、左の列（天文現象）の順に移ります。この順でよいか。
  - 月の満ち欠けの図は月齢から形を計算して描き（右側が光るのが満ちていく月）、日月の出没は 0〜24 時の帯で、太陽と月が地平線の上にある時間を示しています。時刻は文字でも並べています。ワイヤーフレームでは、どちらの図も占位表示です。配色と装飾はハイフィの仕上げ（8.2、8.3）で調整します。
  - 日月の出没は「東京を基準にした時刻」と添えています。サンプルデータと設定画面には利用者の地点がないため、ログイン時も東京を基準にしています（レビュー状態に見送りとして記録）。ログイン時に利用者の地点を使うか、その地点をどこで設定するかを auth-users などの spec で決める。
- **日詳細**：投稿者本人が、自分の一時非表示の投稿をここで見られるようにするか。
- **投稿詳細**：
  - 未ログインで「非表示（本人）」を選んだときは、本人ではないため「非表示（他人）」と同じ案内を出しています。
  - 自分の投稿には通報の導線を出していません。一時非表示の投稿にはコメントの入力欄を出していませんが、いいねのボタンは残しています。
  - コメントの入力欄は投稿へのコメントの 1 つだけで、コメントごとの返信ボタンはまだありません（入力欄はモックで、送信しても保存されません）。
  - 作者が削除した投稿（サンプルの p-111）を開いたときの表示は作っていません（投稿詳細のシナリオにないため）。削除済みの投稿は、本人を含めて一時非表示と同じ案内にするか、専用の案内を作るか。
- **投稿作成・編集**：
  - 未ログインでは、フォームの代わりに閲覧のみの案内とログインへの導線を出しています。
  - 入力エラーは、該当の欄の直下の文言（`aria-invalid` と `aria-describedby` で欄に関連付け）と、フォームの先頭の要約（欄へのリンク付き）の両方で示しています。要約まで要るか。
  - 編集は `?post=ID`（自分の投稿で、削除済みでないもの）で入力欄に値を入れるだけで、見出しは作成と同じ「投稿の作成・編集」です。作成と編集で見出しやボタンの文言を分けるか。一時非表示の投稿も編集できるようにしています。
  - 位置情報を付けないときは、公開精度の選択を隠しています。
- **自分の投稿**：
  - 削除済みの投稿（p-111）も、削除済みのバッジを付けて一覧に残し、編集の導線は出していません。一覧に残すか。
  - カードのリンクは投稿詳細のシナリオに対応する投稿だけが正しく開き、それ以外（p-102、p-111）は投稿詳細の既定の投稿（p-101）を開きます（投稿の部品の仕様）。
  - 公開設定（未ログインのユーザに公開するか）は、状態のバッジとは別の行に文字で示しています。
- **設定**：
  - UI の言語とテーマのラジオボタンは、ヘッダーの切替と同じく選ぶとすぐに切り替わり、ヘッダーの切替とも連動します（保存ボタンを待ちません）。ほかの項目（表示名、投稿の既定値）は保存ボタンで反映する想定です。即時反映と保存の混在でよいか。ヘッダーの切替と設定画面の両方に置くか。
  - 自分の投稿の未ログイン閲覧可否の既定値は 2 択のラジオボタン、位置の公開精度の既定値は投稿作成と同じ 5 段階の選択（初期値は市区町村）にしています。
  - 未ログインでは、設定の代わりにログインを促す案内を出しています。
- **ログイン**：
  - ボタンは文字と中立の丸い印だけで、Google のロゴは使っていません。製品では Google のブランドガイドラインに沿ったボタンにする。
  - 受け取る情報は、Google アカウントの識別子と表示名の 2 つとし、受け取らない情報（パスワード、ほかの Google のサービスのデータ、Google アカウントの位置情報）も並べています。製品のスコープは `openid email profile` 以内なので、メールアドレスを受け取るか（受け取るなら、使い道と公開しないことを書く）を認証の仕様（auth-users）で決める。また、profile スコープでは写真の URL などほかの項目も届くので、製品の文言は「受け取る」ではなく「保存する・使う」情報として書くかを決める。
  - ログイン済み（member）で開いたときは、ログイン済みであることと、トップと設定への導線を出しています。ボタンはモックで、ログインした状態のトップ（`top.html?auth=member`）に移るだけです。
- **通報**：
  - 対象（種類、書いた人、内容）を画面の先頭に出しています。一時非表示の投稿（とそのコメント）は内容を出さず、非表示の案内に置き換えています。
  - 自分の投稿やコメントを対象にしたときは、通報できない旨を出して、フォームを隠しています（投稿詳細では自分の投稿に通報の導線を出しませんが、コメントの通報の導線は自分のコメントにも出ています。部品の側で自分のコメントに出さないようにするか）。
  - 理由は 5 択のラジオボタンで、初期値は選んでいません。詳しい内容は任意です。理由を必須にして、未選択のときの誤りの表示を作るか。
  - 送信後の表示（受け付けた旨、二重の通報の扱い）は作っていません。
- **異議申し立て**：
  - 非表示の理由として、通報の理由と件数を出しています。自動で非表示になったのか、管理者が非表示にしたのかは出していません。
  - サンプルの p-108 は、すでに異議申し立て中（`appealed`）ですが、申し立てのフォームを出しています。申し立て中の投稿では、フォームの代わりに申し立て中である旨を出すか。
  - 自分の削除済みの投稿（p-111）を URL で直接開くと、「非表示になっていないため、申し立ての必要はありません」と表示されます。削除済み用の文言を用意するか。
  - 他人の投稿を対象にしたときは、投稿の内容を出さずに「自分の投稿だけ」の案内を出しています。自分の投稿で非表示になっていないものには、申し立ての必要がない旨を出しています。
- **管理**：
  - 管理帯は管理者にだけ出しています。未ログインと会員には、帯も管理の UI も出さず、権限がない旨とトップへの導線だけを出しています。製品では、権限のない利用者に管理画面の存在を知らせるか（権限なしの表示にするか、見つからない扱いにするか）。
  - 一般の画面との区別は、管理帯と、管理の UI を囲む管理者の役割の色（`--color-admin-band`）の線で示しています。
  - 通報キューは、すべての状態の通報を 1 つの一覧に並べ、即時非表示のボタンは未対応（`open`）の項目にだけ出しています。状態での絞り込みや並べ替え、自動で非表示になった項目の扱いが要るか。
  - 管理者には、一時非表示の投稿の本文も見せています。対象の投稿詳細への導線は作っていません。
  - 異議申し立ての審査は、申し立て中（`appealed`）の項目を通報キューとは別に並べ、「表示を再開する」と「削除する」のボタンにしています。削除の前の確認や、判断の理由の入力欄が要るか。申し立ての内容はサンプルデータの型になく、画面のスクリプトに例文を置いています（データの型に足すか）。
  - 操作はモックで、押すと状態の表示が変わり、ボタンが消えるだけです（画面を開き直すと戻ります）。
- **出典表示・プライバシーポリシー**：
  - 文面は章立てを確かめるための例文で、画面の先頭にその旨を出しています。出典は、ロードマップの技術選定（国立天文台「暦要項」、astronomy-engine、Yale Bright Star Catalogue、地理院タイル、国土数値情報、Open-Meteo）に合わせています。モックの地図は模式図で、地理院タイルは使っていません。
  - プライバシーポリシーの取得項目は、ログイン画面に合わせて Google アカウントの識別子と表示名とし、メールアドレスは載せていません（ログインの論点と合わせて auth-users で決める）。アクセスログの項目、保存の期間、Cookie、お問い合わせの窓口は例です。
- **レビューシェル全体**：`?lang=en` などの URL で開いた言語・段階・テーマは保存されず、画面間のリンクも `?auth` だけを引き継ぎます。そのため、リンクで画面を移ると日本語に戻ります（ヘッダーやレビューシェルで切り替えた値は保存されるので、引き継がれます）。URL で開いた値も保存するか、リンクで引き継ぐか。

## 検査の実行方法

検査には Node.js 22 以降が必要です（モック本体は Node.js に依存しません）。

```sh
cd mockups
npm install                  # 開発用の依存（TypeScript、Playwright）
npx playwright install chromium   # E2E を実行するときだけ
```

| コマンド | 内容 |
|----------|------|
| `npm run check` | 下の 4 つの静的検査をまとめて実行 |
| `npm run check:registry` | 画面レジストリ（15 画面、ファイルの存在、段階の承認順序） |
| `npm run check:tokens` | トークン以外の色・寸法の値の使用 |
| `npm run check:contrast` | トークンの組み合わせのコントラスト比、ダークテーマ定義の一致 |
| `npm run check:i18n` | 辞書のキー（使用キーの存在、日英のキー集合の一致、用語集のキー） |
| `npm run typecheck` | JS の型検査（`tsc --noEmit`、契約は `types.d.ts`） |
| `npm run test:unit` | 純粋なロジックの単体テスト（`node --test`） |
| `npm run test:e2e` | ブラウザでの検査（Playwright、Chromium、`file://`） |

検査は違反を「ファイル:行 内容」の形式で出力し、1 件でもあれば終了コード 1 で終わります。
E2E のスクリーンショットは `mockups/.review/` に保存されます（Git の管理外）。
